# Note style

The note is read by someone who sees the topic **for the first time**. They must understand it fast,
without rereading. Everything else serves that.

## Structure

The order of parts is fixed; it leads the reader from simple to complex by itself:

```
---
tags:
  - <Topic>       # one or two: the main topic, as in existing notes
---
# Title

> _"A fitting quote"_ - Author        <- epigraph, optional (only a strong one, on point)

---

<Intro: 1-3 sentences. What it is and why it matters, in plain words, before any mechanics.
The reader should know at once what this is about and why it is worth reading.>

## Section 1   <- from simple...
## Section 2
## Section ... <- ...to complex

## Comparison ...     <- a table, if the topic has things to compare (optional)

## Worked example ... <- for practical topics: a project from start to finish, commented

## Links              <- links to related vault notes (optional, recommended)

## Sources            <- verified links (required when the facts are not common knowledge)
```

Not every section is required, but the order is: first "what and why", then mechanics, then
comparisons, links and sources.

## From simple to complex

Not a slogan but a way of arranging material:

- **Intuition first, precision second.** Give a simple model or analogy, only then the strict
  definition and details. People hold on to an image and add precision to it.
- **Each section stands on the previous one.** Do not introduce a concept before what it rests on.
- **The abstract through the concrete.** Every abstraction gets an example or an everyday analogy
  ("a closure remembers its surroundings, like...", "a branch is a parallel reality of the project").
- **Start with the problem, not the definition.** Before explaining *how* it works, show *what pain*
  it removes and what existed before: mechanics make sense once the reason is visible. _(Docker was
  born from "it works on my machine but not on the server".)_
- **At the complex end, look under the hood.** Where the topic allows, show the mechanism under the
  syntax: `for x in obj` is sugar over `iter()` / `next()` / `StopIteration`. Go down to the
  implementation **only when it explains observed behaviour** (a mutable default "remembers" because
  it lives in `__defaults__`), not to look clever.

## Micro-style

- **A term in bold, its definition after a colon.** At first mention:
  `**Paradigm**: a point of view on how code is structured and written.`
- **One paragraph, one idea.** Short paragraphs. Break a wall of text into sections and lists.
- **Every sentence carries a fact.** "Essentials in detail" means not one extra word. Remove
  throat-clearing, bureaucratese, the self-evident.
- **Lists for enumerations, tables for comparisons, diagrams for processes.** Do not describe in
  words what is clearer shown.
- **Italics `_..._`** for examples and caveats inside the text.
- **Callout `>`** for the key conclusion or a warning that must not be missed.

## Comparing and combining

- **Compare when there is something to compare.** Three or more comparable things (paradigms,
  commands, approaches) go into a table: columns are criteria, rows are the things. The summary table
  goes at the end of the topic.
- **Combine when topics overlap.** If the new topic relates to an existing note, do not retell it:
  link it and show *how* they relate. A graph of knowledge beats isolated notes.
- **A catalogue is a table too, for lookup.** When a topic has a big family (all built-in functions,
  all dunder methods), put a reference table "item: what it does" at the end.

## Making it visible

- **ASCII diagrams** for processes, states, hierarchies, in a code block:

  ```
  Untracked --git add--> Staged --git commit--> Committed
  ```

- **Tables** for comparisons.
- **Pictures (SVG)** when a picture explains better than text and ASCII: color, 2D geometry, curves,
  gradients, shape. Generated by code, stored in `<Topic>/Diagrams/`, embedded `![[name.svg]]` and
  **always checked by rendering**: see **`diagrams.md`**. They do not replace ASCII: a picture is used
  only where ASCII cannot do the job.
- **Code**: minimal and working. The form of explanation depends on size:
  - *a small snippet*: show the result **in the code**: `sum([1, 2, 3])  # -> 6`.
  - *a larger walkthrough*: step comments in the code (`# 1. ...`), then 1-2 sentences of prose on
    how to read it. Do not hide meaning in long comments inside the block.

## Traps and anti-examples

Often the most valuable part of a topic is not "how to do it" but "how people get it wrong and why".

- **Show the classic mistake next to the fix.** A `# WRONG` block (what breaks) followed by
  `# RIGHT` (how to fix it).
- **Explain the cause, not only the ban.** Not "don't do this" but *why*: the mutable default in
  `def f(x=[])` is shared by all calls because the list is created once, at `def`. The cause is the
  lesson.
- **Form by size.** A single warning goes into a `>` callout; a trap with analysis and a fix goes
  into paired code blocks.

## Worked example (practical topics)

A practical topic (a tool, a technology, "how to do X") **ends with a worked example**: a project or
scenario from start to finish, in steps, with comments in the code, so the reader sees **in what
order** to do things and **how to read** such code. Each step is its own artifact (a file, a
command); the example is whole and runs.

## Internal links

Connectedness is half the value of a note in Obsidian.

- Link your notes: `[[Note]]`, a section `[[Note#Section]]`, with a label `[[Note#Section|readable text]]`.
- The first mention of a term that has (or should have) a dictionary note is a link `[[Term]]`.
- In "Links", 2-5 links to related topics, each with one line on *how* it relates:
  `- [[Databases]]: SQL as an example of a declarative paradigm`.
- No links for the sake of links: a link must carry meaning.

## Sources

So the reader can check and go deeper, and the note stays trustworthy.

- **Check on the web** (WebSearch/WebFetch) before inserting a link. Never invent a URL.
- **Priority:** official documentation and primary sources, then authoritative books, then
  peer-reviewed research, then good reviews. Random blogs only as a last resort and with a caveat.
- **Format**: a list at the end:
  ```
  ## Sources
  - [Python Docs: Data model](https://docs.python.org/3/reference/datamodel.html)
  - Lutz M., Learning Python, 5th ed., ch. 4
  ```
- Common knowledge needs no source. A number, a date, a quote or a disputed claim always does.
- Unsure of a source: mark it "needs checking" rather than give a false link.

## Avoid

- **Filler**: "it should be noted that", "in today's world", "as is well known".
- **Walls of text**: long paragraphs with no structure.
- **Duplication**: if the topic is covered, link it.
- **Premature complexity**: terms and details before the reader is ready.
- **Cards inside the note**: cards live separately (`cards.md`).
- **Manual line breaks inside a paragraph**: an enumeration is a list, not a ladder of short lines.

## A small sample in the right style

```markdown
## Variables

Binds a name to a memory address that holds a value: an alias for that value.

    pi <- 3.142

Reserves a block of memory, writes the value and binds the name to it.

### Typing

A type tells the program how to interpret the bits in memory and helps catch errors.

- **Static**: the type is declared (`float pi`), errors show at compile time. _C, C++_
- **Dynamic**: the type is checked at run time. _Python, JavaScript_
```

Note: intuition ("alias") before mechanics, terms in bold, definition after a colon, the example
explained after the code, the two kinds of typing compared in a list, nothing extra.
